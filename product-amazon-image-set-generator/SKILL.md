# Amazon image sets

Own scope, image planning, coverage and the production queue. Reuse existing plan/spec/state records; derive summaries instead of adding parallel plans, status stores or workflow services. `product-image-project-builder` owns product evidence; `product-single-image-generator` owns generation and visual QA. Reuse the current package and known requirements.

Activate supporting instructions according to the current task and information gap. Preserve complete guidance and examples for the cases that need them; text/file size is not a reason to remove useful requirements. Follow links when planning, designing, inspecting or troubleshooting requires that material, not as a checklist to load the whole skill directory. Reuse completed intake, saved image ledgers and resolved current-image packets. Revisit source material when the evidence, task or criteria change, or a specific uncertainty needs verification.

## 1. Resolve the requested work

Use the user's instruction or saved scope: Gallery, A+, or both. Product initialization can precede this choice. Before set planning/generation, ask once whether the user wants Gallery, A+, or both only if the instruction and saved state leave scope unresolved; save and reuse the answer. An A+ example alone does not request A+ production. A standalone image goes to the single-image skill; an explicit pilot keeps its requested count.

For a full Gallery request, default to complete applicable coverage, with the image count derived from the decomposed content. Produce the supported applicable modules for the user to select afterward; do not silently choose a smaller subset or compress to nine. Check product views, all meaningful selling points, product character, size/model selection, actual variants, evidenced use when relevant, and distinct lifestyles. The initializer supplies an editable 11-image seed, not a cap or a claim that every topic applies. Follow [complete Gallery coverage](references/amazon-planning.md#complete-coverage-before-user-selection). Premium A+ retains its normal 13-image policy within 9–15. Explicit exclusions, counts and pilots keep their scope; resolve coverage/count conflicts visibly. Expanded mode (30–40 per channel, fallback 36) still requires an explicit large-production request. New defaults never expand a saved queue.

For this department, A+ delivers only a code-exported 1464×600 PNG. Generate a suitable wide composition, retain the original and run the single-image [code export](../product-single-image-generator/references/state-and-contract.md#mandatory-a-code-export) before review; model-native pixels are not trusted as final dimensions. Matching ratios resize proportionally without cropping; mismatched ratios crop around required content and resize proportionally, without stretching or padding. Gallery uses its own canvas (square by default). Archive older/mobile canvas requirements without producing extra versions. Select the current delivery language from the task/market; archived translations do not request additional outputs. Deliver independent files for design-team assembly. Each may contain related panels, copy, graphics, comparisons or steps serving its assigned task.

Prioritize **2.44:1 (1464:600)** landscape framing during A+ generation, before style/reference framing or local layout choices. Put it first in every image prompt and use supported size/ratio controls when available; follow the single-image [export guidance](../product-single-image-generator/references/state-and-contract.md#mandatory-a-code-export) for tool limits. Exact delivery pixels still require code export.

New A+ contracts require source/crop QA before export. Use the packet's source-review path and the single-image [guarded export workflow](../product-single-image-generator/references/state-and-contract.md#mandatory-a-code-export); projected geometry and recorded judgment must permit the crop, then the final image receives its own QA. No automatic segmentation service is assumed.

## 2. Turn responsibilities into an image plan

**Content group ≠ output image.** Seven module descriptions are seven responsibilities, not seven photographs. Use [A+ grouping](references/a-plus-module-layout.md#page-skeleton-and-seven-responsibilities) when establishing/revising grouping: product introduction → core material/benefit → structure/craft → function/use → range/fit → lifestyle. Plan the explanation-rich upper section and the scene-led closing section before individual pictures; style varies within this skeleton. A complete saved ledger can be reused directly. The initializer's A+ nine-image seed `1+1+2+2+1+1+1` is a draft to adapt to this flow before approval, not the final page order or required content list. Gallery uses [its own complete coverage and state handoff](references/amazon-planning.md#gallery). Only its first two white displays default to upright front/reverse poses for the Gallery opening workflow. Other poses remain free, including flat-lay or upright variant arrangements. Follow the Gallery guide for mandatory opening-pair user approval and product-state handoff; later images inherit supported identity, not the pair's pose/layout. AI designs selling-point, parameter and style combinations from product evidence and the current brief; finished examples are optional.

Use the builder's [automatic execution strategy](../product-image-project-builder/references/automatic-intake.md#automatic-execution-strategy) to record each child's `execution_policy`. A supplied design document and useful multi-view evidence favour ADVANCED; vague/sparse input calls for AI_ASSISTED to fill authorized creative gaps. Select through natural-language analysis, not file-count rules. Preserve required content and exact supplied copy in either mode. Evidence-insufficient children remain pending; supported children may continue without downgrading the entire set.

Before generation, save the selected image count and a compact ledger: group → child image IDs → buyer question/required proof → visual treatment/copy → status/output. Child counts must sum to the selected target. Generate and count child IDs, not group headings. Missing evidence stays visible on affected tasks; do not invent a variant, size, operation or care claim, or substitute an unrelated macro under that label. Explicit replanning updates the responsibility and its reason.

For A+, record what each group inherits, explains and leads into using existing sales-task/brief text. Explain products through whole-product orientation → relevant detail and purpose → evidenced use. Distinguish narrative continuity, shared visual edges and actual cross-boundary objects; carousel slides must each work with the fixed neighbours. Allocate additional images to the corresponding detail/selection/scene carousel without changing the page flow merely to meet a count. Follow the [continuity guidance](references/a-plus-module-layout.md#explanation-use-and-continuity); no second plan or new required schema is needed.

For mixed requirement sheets/redesigns, read the builder's [intake workflow](../product-image-project-builder/references/automatic-intake.md). Carry the supplied scope/count, `content_groups` and decomposed `modules` forward. The planner resolves an unspecified target, then checks actual child count, group coverage and fact gaps; readiness is computed from these records rather than stored as another state object. Keep source copy verbatim in its selected language; Chinese analysis is not image lettering. Originals establish product truth; design references guide only their assigned visual elements. Old layouts remain archival in a redesign unless currently requested.

Reuse the builder's atomic facts/selling points; do not reparse all uploads for each image. Map required features and buyer questions onto the existing children before choosing scenes. Identify what the picture should visibly communicate and what belongs only in exact copy. Mix these treatments within an image when useful. Pure atmosphere is allowed when assigned, but cannot replace required feature, operation or selection information. Do not force every selling point into visual effects, impose a lifestyle quota, or attach the full selling-point list to every prompt.

## 3. Design before generating

When creating or revising design decisions, use [visual direction](references/visual-direction.md) to set one shared visual language and each image's `creative_brief`: concept, visible device, hierarchy, graphic treatment, contribution and success criteria. Execute an already complete brief through its current task packet rather than reopening design planning for every image. Default to `adaptive`; derive composition from the job. Fix the shared background lightness/colour family, warm–cool balance, contrast/shadow range and type family in the existing `visual_system` before individual design. Per-image adjustments and catalog styles stay within those boundaries; composition, scene, camera and surface may vary. A request for unified backgrounds does not permit independently alternating dark and light pages. A material image, selection guide, operation and lifestyle need their own visual proof within the shared language. Full lifestyle assignments need recognizable people/actions/environments and a readable, naturally scaled product.

Use [autonomous execution](references/autonomous-design.md) for research or an internal pilot. AI chooses reversible design details and checks representative images; Gallery must obtain opening-pair user approval before its remainder, while A+ keeps its existing pilot policy. Consolidate only necessary product-truth/scope questions; continue independent tasks. Image acceptance still requires real human feedback.

Optional references, only when needed: [style/reference integration](references/product-led-style-integration.md), [catalog layouts/styles](references/design-library.md), [template constraints](references/generation-templates.md), [claim wording](references/claim-safety.md). A catalog selection does not complete the creative brief.

For multi-style/colour product displays in either channel, use [variant design](references/visual-direction.md#multi-variant-product-design): swatch cards supply scoped variant evidence, required choices appear as actual products, and task-led composition stays within the established set background/light/type. Use the `variants` task role even with a generic template.

## 4. Execute in the available environment

**Web chat:** read [browser testing](references/browser-testing.md) and use the same ledger with available tools. Do not load the local runtime/schema references unless actually running scripts. Ordinary attachments do not install skills or grant local tools. Check actual image viewing and image-tool attachment support once; report capability limits honestly.

**Script runtime:** read [state handoff](references/state-handoff.md) once; use [schema](references/set-plan-schema.md) only while editing records and [source/state details](references/input-and-state.md) for provenance problems. From this skill's directory:

```text
python3 scripts/init_visual_set.py <package> --set-id <set> --deliverable a-plus --count <selected-count>
python3 scripts/init_visual_set.py <package> --set-id <set> --design-input <filtered-DESIGN_INPUT.json>
python3 scripts/validate_set_plan.py <package> --set-id <set> --approve
python3 scripts/set_runtime.py <package> --set-id <set> next-generation
python3 scripts/set_runtime.py <package> --set-id <set> prepare --module-id <returned-id>
```

Choose one initialization route. A completed single-channel filtered brief imports its actual image IDs, grouping, copy, roles and evidence links; an undecomposed brief must be finished first. Without it, initialization creates a seed for AI to adapt. `--deliverable gallery/both` selects those channels; per-channel count flags override `--count`. Resume existing work instead of initializing it again. `--approve` pins an executable plan internally, not human image acceptance.

For a new full Gallery set, load and follow the [single-image skill](../product-single-image-generator/SKILL.md) to generate the upright front/reverse pair, inspect against originals, display both actual outputs, and stop for explicit user approval under [Gallery guidance](references/amazon-planning.md#opening-pair-inspect-first-inherit-identity-rather-than-pose). No remaining Gallery generation is authorized until both current images are approved. For an older unmarked Gallery project, explicitly revise the plan or create a new set to adopt this policy before continuing; do not bypass it by merely resuming the legacy queue. The runtime enforces this boundary for marked plans but cannot judge pixels or infer human consent. After approval, batch production uses `next-generation` to select an unproduced child. Ordinary `next` prioritizes pending review; a repeated ID requests inspection, not another generation. Send only the current packet's prompt and actual listed images to the generator. Re-establish this child's role before each call; previous outputs/history are not automatic references. The scripts prepare records and packets; they do not launch image generation or erase chat context.

Structure feedback uses the single-image [state-transfer interface](../product-single-image-generator/references/state-and-contract.md#structure-state-transfer). Synchronization compares each child's required locks with its pinned snapshot: changed/unresolved dependencies block that child, while unrelated children can continue. Revise affected approved tasks from current state; never silently inject new facts into old contracts. A rejected image alone does not change product truth; first distinguish a generation defect from an incorrect/incomplete product interpretation.

## 5. Review, correct and deliver

Use single-image QA on actual pixels: product truth, relevant anatomy/hardware/operation, exact copy and canvas, buyer-question coverage, role fit and design quality. A script pass verifies records, not appearance. Keep candidates pending human review while producing other authorized tasks, except that Gallery must pause after its opening pair until user approval. Focused feedback authorizes correction of that image; reuse evidence and preserve unrelated outputs. Pinned changes need a local revision; retry limits and acceptance records follow [state handoff](references/state-handoff.md).

Use the review packet's `review` disposition before invoking visual inspection again. `REUSE` preserves the saved result, including failures or uncertainty; it does not accept an image. `INVALIDATED` requires inspection against changed inputs. Actual composition observations belong in single-image QA, not generation prompts; use this child's existing role/layout rather than universal product-size or centering rules.

Before handoff, reconcile target/planned/generated/deferred counts, responsibility coverage, repeated messages and visual rhythm. Compare the actual images together for background lightness, colour temperature, contrast/shadows and typography; an individually attractive image that drifts from the shared range needs a focused correction. Deliver files with grouping, copy guidance and clear statuses. `set_runtime.py ... handoff` returns the manifest; it does not stitch, upload or certify the assembled page. Call unreviewed images drafts; never fabricate human acceptance.

For complete Gallery delivery, identify each image's purpose and covered information so the user can keep or omit it after viewing. Reconcile every applicable responsibility with actual outputs or an explicit unresolved gap; do not label the set complete while fit/model guidance or another applicable topic is missing. Selection for use is separate from visual acceptance and does not delete generated files or rewrite QA history.

After generating executable work, include the [data gaps/conflicts table](references/amazon-planning.md#data-gaps-and-conflicts-at-delivery): image ID/responsibility, issue type, exact missing field or both conflicting statements with sources, affected content, delivered/deferred scope, and the precise information needed. Include a no-issue row when none is found. Separate data gaps from tool/runtime interruptions, report actual counts and remaining IDs, and continue unaffected authorized images rather than requiring a routine continue message. Use existing records; the table is a delivery summary, not another approval stage.
